homepage

(old homepage)

The wrong forms up front. “Recently updated” only ever meant “last edited”. Once a form is published, people care about other things — how many responses came in, for one

A decorative homepage. Half the page was filler; the useful part was the list

Two ways to create, both confusing. A button in the header and a gallery of templates. The button only ever made an empty form; templates could make anything, but looked like flat pictures

An incomplete list: no groups, no templates, filters that never stick. People’s workflows rarely change, so re-applying the same filters on every visit got old fast. Groups are part of that workflow too

(old list)

My actions

01 — Dug into the history

It turned out the homepage had been built for the B2B version of the service — a landing page describing what Forms could do. When the product split into external and internal versions, that page was carried over untouched.

02 — Wrote the interview guide and worked through
what came back

  • People group forms by topic or by the team that owns them. They run recurring surveys with identical names, and the group is what tells them who touched a form and when. Today those are two separate lists, which is a constant annoyance
  • Sorting by last edit isn’t much use. Everyone works differently depending on how many forms they juggle: some want the ones with new responses first, others sort by response count
  • People duplicate a form and tweak it slightly, so the names stay identical. They need some other marker to tell them apart
  • When there are only a handful of forms, a table view is overkill

03 — Formed a hypothesis: nobody needs this homepage

What people actually want is a dashboard that highlights what changed. But a dashboard needs its own discovery round, and we had neither the time nor the budget — so the list was the place to invest. It’s the main tool anyway

04 — Dug through Yandex.Metrica (GA analogue)

The list beats the homepage and gets bookmarked: 17% of visits against 4%. Creating from a template and from scratch are equally popular. Filters get adjusted constantly — on almost every visit

So what's the design?

The list is the new homepage

No more bookmarking, no more hopping between pages

One place to create

An empty form is really just a template with no questions, so I put every template in one place, in one style. Visible but compact, so it doesn’t steal room from the list. And built to grow — including with templates people make themselves.

Customizable

View the list as a table or as cards, depending on what you’re doing. I added a grouped view too

Groups are always
visible

A column of their own in table view, a heading in grouped view

editor

(old homepage)

Hard to scan, hard to change. You only saw the question type — number, choice — so two questions of the same type were impossible to tell apart. People look for the wording first, not the type

Order was hard to manage: new questions only went to the end. No auto-scroll, no animation, no hint. Moving one meant drag-and-drop that was badly built, in the design and in the code alike

(old list)

Settings were buried: images, hints, answers and type-specific options all lived in a popup. Checking or editing anything meant opening that popup for every single question

Conditions were invisible unless you clicked an icon. Some questions should only appear after a particular answer — and that icon was one most people never noticed

No conditions for a whole page. People had been asking to show or hide an entire step of the form based on an answer. It simply wasn’t supported

My actions

01 — Read the feedback

Went through what users had already told us, and shaped the research hypotheses around it

02 — Took apart how questions are built

Looked at how questions work under the hood: what data each type holds and how it’s stored. Many types turned out to differ by a single setting — email and phone, for instance, are plain text fields with different validation

03 — Looked at the numbers

Asked the PM to pull stats on how many questions and pages real forms actually have, so navigation and the flow for adding things could be designed around reality

04 — Dug through Yandex.Metrica (GA analogue)

Which questions get created most, and with which settings. Then I gave each one a top-level type: text, choice, number and so on

05 — Ran the UX research

Wrote the full script for the prototype study, then built an interactive Figma prototype: animations, the new drag-and-drop, and the harder flows like adding logic at different levels

So what's the design?

A richer card,
edited in place

I moved the title, answers and the settings people actually use onto the card itself, and hid the rare ones. The layout is block-based and consistent: shared blocks are always there, type-specific ones come after them. Nothing to relearn when you switch types. Win!

Everything is edited right on the card, and it all saves by itself

Fewer types

Cut question types from 27 down to 8. Each one adapts to its data type through settings or validation instead. Every type got an icon and a color, so a form is far easier to scan

Conditions you can see

Added conditions for a whole page. A question’s conditions sit on its card, a page’s at the top of the page. Any condition collapses down to its heading — easy to find, never in the way

Flexible ordering

A question can go anywhere in the form now. Each card has two hover zones that reveal the matching add-question button

Useful navigation

Instead of a bare list of questions, I built proper navigation for the editor, showing both the type and the text of each one

Nested questions are shown as nested.
Questions can be added and deleted from here.
Clicking one scrolls the editor to its card.
And best of all — questions can be reordered straight from the panel

styles

(old style)

Barely anything to customize. People wanted control over colors, spacing, the required-question marker and plenty more

Opaque settings: every parameter used the same control, a slider. No value shown, no preview of the result — it raised more questions than it answered

(old style list)

Color names that told you nothing. Themes get set up rarely, and the names gave no clue which part of the interface would change. The palette was too small, and the settings were scattered across the screen

A preview that previewed very little. No real spacing, no card for the form to sit on, no service header

Dated presets. Colors too loud, contrast too low, tired backgrounds and low-quality images

My actions

01 — Ran quick UX tests

Hallway tests, side-by-side comparisons, surveys in Pathway. The hypotheses held up, including on the numbers

02 — Dug through Yandex.Metrica (GA analogue)

To see which themes and which parameters people actually use

03 — Studied the themes people built themselves

To understand what they were really after. Some forms were styled with hand-written CSS,
so the frontend devs exported every property people had used

04 — Pulled it all together

From the analytics, the UX work and those custom styles I built the final list of properties, ranked by how often people needed them

So what's the design?

A proper palette

Pulled every color into a block of its own, and showed which element each one actually paints.

Added palette generation: if there’s a brand color, one value repaints every control in the form

By default you only see the three colors people reach for most. Need finer control — expand the rest. Nobody gets buried in options they’ll never touch

Easy to scan

Parameter values are shown, not described. People call the same property by different names, and nobody can guess what a slider’s range means — it’s simpler to show every option

Simpler navigation

Grouped the properties by what they affect: text, background, buttons. Much easier to find things.

And for everyone who doesn’t need fine-grained control, there’s a separate block with the properties people reach for most

A spec for the developers

Documented every animation, and how to automate color selection for the default themes we’d add later. Built working prototypes in CodePen

Theme migration

Backward compatibility meant the developers couldn’t build some of the new properties straight from the mockups. Themes are stored as JSON, so I proposed rewriting that JSON once during the migration: save people’s custom themes as service themes. Nobody lost their data, we shipped the new editor, and everyone got room for one more theme of their own. Win-win :)

Contrast check

Proposed a specific npm package: it checks contrast between text and background, controls and background, and text inside controls. WCAG-based

Form appearance spec

A detailed guide to how every element behaves under different settings, and what the edge cases look like. It also cleared up a few long-standing display problems — for example, how to render a control without a border: I added an option to remove the control’s inner padding, and documented that in this case the standard control is swapped for the borderless one already in the library.
